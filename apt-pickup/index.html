1하나의 시트, 두 개의 입구

두 PRD가 다른 건 시점이지 물건이 아니다. 예약 생성 시점과 실시간 매칭 후 시점이 같은 시트를 띄우고 같은 값을 만든다.

{지상|지하, 층, 동} → “지하 2층 · 101동 앞에서 탈게요”

PRD① 요구사항 / PRD② 예상 솔루션 1~2단계

2칩이 먼저, 입력은 폴백

빈 입력 필드는 “뭘 적어야 하지”를 못 푼다 — 지금 요청사항 필드가 실패하는 방식 그대로다. 답을 보여줘야 한다.

단지 데이터가 있으면 동 칩, 없으면 같은 자리에 숫자 키패드. 커버리지 0%든 100%든 같은 UI라 출시가 데이터 진척도와 분리된다.

신규 유저 픽업위치 언급률 13.0% vs 기존 47.5% (PRD①)

3두 번째부터는 확인만

아파트는 대부분 집이다. 아파트 출발 실시간 유저의 40%가 2회 이상, 그중 28.8%가 5회 이상. 매번 같은 안내를 반복 중.

같은 주소 재방문이면 프리셋이 완성된 채로 뜨고 1탭 전송. 예약에서도 미리 채워져 등장한다.

아파트 출발 실시간 유저 5,985/16,657명 (PRD②)

4휘발 문제 — 채팅이 아니라 운행 정보로

픽업 위치는 “메시지”가 아니라 이 운행의 속성이다. 채팅에 쌓으면 시간순으로 밀려나고 운전 중 스크롤을 시켜야 한다.

출발지 주소 바로 아래 고정 슬롯에 남기면 오버레이가 사라져도 정보는 남는다. 예약에서 온 값과 실시간에서 온 값이 같은 슬롯에 들어가 드라이버는 한 번만 배운다.

PRD② 논의 요청 사항에 대한 제안

5출입구까지 담아야 46%가 다 들어온다

픽업위치 언급은 넓게 46.0% / 좁게(주차장·지상·지하) 37.5%. 그 차이 약 8.5%p가 “정문·출입구” 어휘 — 지상/지하 이분법으로는 못 담는다.

대단지는 출입구가 3~5개고, 동을 아는 거주자도 진입 지연을 피하려고 정문을 부른다. 출입구를 고르면 동 선택은 건너뛴다.

게이트 번호·상가 앞 같은 나머지는 “그 외 안내” 한 줄로 받는다. 자유 텍스트를 없애는 게 아니라 이 필드 안에 가두는 것이 핵심 — 요청사항으로 다시 새지 않게.

PRD① 데이터 근거 / 미커버 패턴: 차량 진입 통제, 시간대별 게이트 개폐

6지하는 “지정”이 아니라 “부탁”이다

단지는 사유지라 기사에게 진입 의무가 없다. 기사들이 꺼리는 이유가 분명하다 — 주차 차량·구조물에 가린 사고 위험, 보험료, GPS 미수신, 회전율 대비 요금은 100~200원 차이.

그래서 유저가 지금 전화로 부탁하는 것이다. UI가 “고르면 끝”처럼 보이면 안 된다.

지하 요청일 때만 드라이버 응답을 “지하로 갈게요 / 지상에서 뵐게요”로 바꿔 협상을 UI 안에 넣었다. 거절하면 픽업 지점이 지상으로 조정돼 슬롯에 남는다.

출입구 이름도 단지마다 달라 정문·후문 + 직접 입력으로만 둔다. 방위문(동문·서문)은 안 쓰는 단지가 많다.
